## 二、结论：Token 大头在哪

1. **成本大头 = flash 模型 × 缓存读取**
   - flash 承担主对话 + 所有执行子代理（75% 成本）
   - Cache Read 704M vs Input 8.8M：**每次消息都把整个上下文重读一遍（命中缓存）**，上下文越臃肿、每轮重读量越大
2. **少数大会话主导**：Avg 10.5M vs Median 289K（36 倍）——长开发会话（多子代理 + 大工具输出）消耗绝大部分。**当前开发会话即为典型大头**（累计 cache 1.7 亿、约 $1.45）
3. **工具层块头**：
   - `bash` 输出（构建日志、git diff 全文）是上下文大块头
   - `read` 整文件（大文件尤其）
   - `background_output` 拉子代理完整报告（200KB+ 截断后仍大量进上下文）

## 三、优化方案（按性价比排序）

| #   | 动作                                                                  | 效果                                    | 状态                    |
| --- | --------------------------------------------------------------------- | --------------------------------------- | ----------------------- |
| 1   | **压缩已闭环会话部分**（开发/调查/修复全过程 → 摘要）                 | 每次对话 cache 读取骤降，砍掉最大体积源 | ✅ 已执行（2026-08-03） |
| 2   | bash 输出始终截断（`Select-Object`/tail/`git diff --stat`），只留结论 | 减少单次工具输出进上下文                | 持续                    |
| 3   | read 只读关键段（limit/offset），大文件用 codegraph/摘要代替整读      | 同上                                    | 持续                    |
| 4   | `background_output` 只用 `from_end` 拿结论，不拉全文                  | 避免单次几十万 token 进上下文           | 持续                    |
| 5   | 子代理 prompt 明确"少探索、直接产出"                                  | 降执行任务成本                          | 持续                    |
| 6   | 长时间会话适时开新会话（带 handoff 文档），避免上下文无限累积         | 从源头控制 cache 读取                   | 建议                    |

### 预估收益

- 方案 1（压缩）：本会话后续每轮 cache 读取显著下降（目标 -50%~70%）
- 方案 2-4（工具节制）：单次工具调用进上下文体积下降（大输出场景 -80%+）
- 方案 6（会话拆分）：长开发项目按阶段开会话，每会话保持 <50 万 cache
