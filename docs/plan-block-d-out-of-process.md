# PluginLab 块 4：D 进程外托管工作文档（设计门）

> 2026-08-08 制定。路线图总览见 `docs/roadmap-next.md` 块 4。**本块设设计门（P0 风险 R3）：必须 brainstorming 定架构后才允许拆票实施**。本文档只承载：设计问题清单、候选方案、验收基线、与既有机制的关系——不写实施步骤。

## 背景与目标

Pianoteq 类插件（宿主杀手）在加载/测量时调用 `ExitProcess`/abort，进程内任何保护（/EHa、catch(...)、看门狗）都无法拦截——唯一的根治是把 VST3 托管进**子进程**：插件崩溃/自杀只杀子进程，宿主存活并可重启续测。

**验收基线（roadmap）**：Pianoteq 可加载测量不杀宿主；子进程崩溃自动重启续测。

## 设计问题清单（brainstorming 必须逐条定案）

### 1. 子进程边界：scan / load / measure 哪些进子进程？

候选拆分：
- **A. 全量进子进程**：scan + load + measure 全在子进程——隔离最彻底，但扫描（本就脆弱）与编辑器（GUI）都跨进程，复杂度最高
- **B. 仅 load + measure 进子进程**：扫描留宿主（现有看门狗/黑名单机制不动）——Pianoteq 场景就是"加载即自杀"，扫描阶段它已被黑名单拦截不加载；测量阶段子进程加载+处理
- **C. 按插件白/黑名单动态决定**：已知宿主杀手（Pianoteq 黑名单）才进子进程，其余插件仍在宿主进程（零开销）
- 倾向：B 或 C（最小侵入），A 作为终态目标

### 2. 编辑器跨进程托管（R3 公认难点）

- VST3 编辑器窗口是插件 DLL 创建的 HWND——子进程中创建，宿主怎么显示？
- 候选：
  - **a. 编辑器留宿主、测量进子进程**：load 分两段——子进程加载实例（测量用），宿主进程再独立加载实例（编辑器用）→ 双实例内存开销 + 参数同步问题
  - **b. 子进程窗口跨进程嵌入（SetParent HWND 到宿主）**：可行但脆弱（消息循环、焦点、DPI）
  - **c. 编辑器降级 GenericAudioProcessorEditor（宿主进程）**：无原生 UI，但 AI 驱动主路径不需要原生编辑器
  - **d. 子进程内自建窗口（独立顶层窗口）**：简单但用户交互割裂
- 倾向：c（AI 驱动主路径无编辑器需求；原生编辑器仅人工使用场景，可后置）

### 3. 与既有机制的关系

| 机制 | 现状 | 子进程化后 |
|------|------|-----------|
| 黑名单（addToBlacklistLocked + saveCache） | 宿主进程内，扫描/加载超时触发 | 子进程崩溃 → 宿主记录崩溃 → 黑名单/死马踏板联动 |
| 死马踏板（deadMansPedal） | JUCE scanner 内部 | 子进程化后 scanner 位置未定，踏板语义需重定 |
| 看门狗（scan/load 超时） | 宿主消息线程 Timer | 子进程场景下超时检测点转移（进程存活 + 进度双条件） |
| 测量路径异常保护（块 C 任务 1） | 宿主内 /EHa + catch | 子进程内同样需要（防子进程内 C++ 异常逃逸）——但进程隔离后宿主侧不再需要 |
| CrashLog / minidump | 宿主 | 子进程崩溃日志经 IPC 上报宿主统一记录 |

### 4. 进程崩溃恢复语义

- 子进程崩溃（exit code 非 0 / 管道断开 / 心跳超时）→ 宿主记录 + 可选自动重启续测
- 重启后插件参数状态丢失——恢复语义：从最后一次参数快照（captureParameterSnapshot）恢复？
- 连续崩溃上限（防崩溃循环）——复用扫描挂起上限（kMaxScanHangs=3）语义？

### 5. IPC 协议扩展

- 宿主 ↔ 子进程通道：复用 Named Pipe 协议（PluginLab↔子进程），或更轻的 stdin/stdout JSON 行协议（子进程无 GUI 依赖）
- 子进程生命周期命令：start/stop/restart/status（心跳）
- 批量采集（块 A）的 dataset 管线对子进程的感知：透明（宿主 CommandParser 不变，内部路由到子进程）？

### 6. 音频路径

- 子进程内 processBlock 的干/湿数据回传宿主：逐 block IPC（大流量，48000Hz×512 采样×2 声道≈8MB/s）？还是子进程内录制完一次性回传？
- 倾向：子进程内录制（复用 SweepRunner/CaptureBuffer）→ 结果 JSON 一次性回传——流量最小，且分析器可留子进程或宿主（分析器无插件依赖，留宿主）

## 候选架构草图（brainstorming 输入，非定案）

```
宿主 PluginLab（现有）
├── CommandParser（不动，前端协议不变）
├── ChildProcessCoordinator（新）── 子进程生命周期 + IPC + 崩溃恢复
└── 子进程 PluginHostChild（新可执行，VST3 宿主瘦身版）
    ├── 加载（/EHa 保护）+ 测量（SweepRunner 复用或拷贝）
    ├── 结果 JSON 回传
    └── 心跳上报
```

## 实施顺序建议（设计门通过后）

1. **D0 设计门**：brainstorming 定案（边界/编辑器/崩溃恢复/IPC），产出 ADR 记录
2. **D1 子进程骨架**：PluginHostChild 最小可执行（加载 TestPlugin/真实插件 + 心跳 + 退出码上报），宿主 ChildProcessCoordinator 启动/探测/回收——验收：子进程可启动、崩溃可检测
3. **D2 测量入子进程**：freq 测量在子进程完成、结果回传——验收：Pro-Q 4 经子进程测量结果与宿主直测一致（<0.5dB）
4. **D3 崩溃恢复**：子进程中途崩溃 → 宿主检测 + 自动重启 + 续测——验收：模拟崩溃（TestPlugin 注入 ExitProcess？）宿主存活且重启续测
5. **D4 Pianoteq 实战**：真实 Pianoteq 加载测量不杀宿主——roadmap 验收
6. **D5 编辑器降级/嵌入**（可选，取决于设计门定案）
